# Ticket 184 implementation

## Work contract

- Outcome: issue #184, Show the CLI's tools and approvals in DSH, under spec #179 only. Base: `feat/179-access-methods` at `137585c`. Branch: `feat/184-cli-tools-approvals`.
- Owner decisions (2026-11-12): tool activity is inline markdown in text blocks (criterion 1 amended on the issue); real DSH tool cards moved to #210 (blocked by #184, `ready-for-human`) because DSH's public `StreamChunk` and `ToolCallBlock` types cannot express a tool call the provider already executed and the only public route (`Session.append` rows) must first be tried live. Approvals and questions use `ctx.approval.request` and `ctx.userQuestions.ask` over the CLI's stdio control channel, no MCP server.
- Allowed writes: Claude CLI driver, translator, a control module, provider capabilities, tests and fixtures, regenerated build output, changelog and state documents. No DSH changes, installed state, real credentials, main merge or release.

## Behaviour

- **stdin contract.** The subprocess service accepts `stdin: 'ignore' | 'pipe' | { data }` (published `@deepseek-ai/dsh-subprocess-local` 0.2.2-rc.1, read from an on-disk package checkout, not the app archive: `pipe` exposes a writable `stdin`, `{ data }` is written then ended). #182 sent `{ text }`, which that service does not read, so the prompt would have reached a real CLI as empty input. The driver now uses `pipe`, writes the user envelope, keeps stdin open for control replies and ends it when the `result` frame arrives. The test runtimes follow this contract.
- **Tool activity.** The translator draws each `tool_use` (bold name, file or command, remaining arguments) and each `tool_result` (fenced, clipped, marked error when failed) as a whole text block in stream order. Streamed text is not repeated from the completed message. No `tool-call` chunk is ever emitted, so DSH runs nothing.
- **Approvals.** `--permission-prompt-tool stdio` makes the CLI send `can_use_tool` control requests. The driver answers them without blocking the stream: `ctx.approval.request` with the session agent, tool name, call id and a reason. `allowed-once` is `allow` with the original input, `rejected` is a deny, and `cancelled` and `unavailable` (and a missing service, an unknown agent or a throwing dialog) are a deny whose message starts "Nobody refused this action". Under DSH's approval policy `never` the deny says no prompt was shown.
- **Questions and plan review.** `AskUserQuestion` goes to `ctx.userQuestions.ask` through a small local interface and returns `answers` keyed by question text. Answer semantics follow DSH's question service: on a single-select question a typed answer replaces the choice, on a multi-select it is added to the selected labels, and an item with nothing selected and no text is a skip (a skipped question denies). A dialog DSH cannot show (for example a subagent, which may not open human interaction) denies saying so, never "cancelled". `ExitPlanMode` is a `plan-review` question with the plan as detail: approving allows; keeping the plan denies with the Owner's feedback. A missing service denies with a clear message, and a plan with no text is sent back rather than waved through. The plan-review words are Arabic or English following DSH's language (`locale.preference` read through the settings service); any other or unreadable language gives English.
- **Permission mode.** Provider capabilities declare `permissionModes`: `read-only` to `plan`, `workspace-write` to `acceptEdits`, `danger-full-access` to `bypassPermissions`, fallback `default`. The policy is read from the `Current DSH file policy: ...` line of the request (a DSH text convention, not an API) on every turn, so a change applies from the next turn. A missing or unrecognised line gives `default`, never a more permissive mode. Messages whose source kind is `user` (what the person typed or attached) are never read for the line, so nothing pasted into a prompt can choose a mode. The three new flags are optional: an older CLI without them still runs and denies what needs a prompt.
- **Abort and withdrawal.** Each dialog carries the turn's signal plus its own. Aborting the turn, the CLI's `control_cancel_request`, an exception or the end of the turn aborts it, so none stays open, and no reply is written after the turn ended. A 15 s keep-alive stops a person's thinking time from tripping the idle watchdog while a dialog is open.
- **Attachments.** The last user message's images are resolved through the attachment service (same limits as the direct route) and sent as base64 image blocks next to the text; files rely on DSH's documented projection (dsh-llm `FileBlock`: request assembly turns every file into handle text with name, size and a read-only saved path, so adapters see text); the adapter adds no file handling and the tests feed that text by hand.

## Review

Independent Standards and Spec review (two sub-agents on `claude-code/claude-sonnet-5-5`, the only authorized route) against `137585c`. Fixed: the permission-mode line could be chosen by pasted text (typed messages are now ignored for it); the empty-plan silent allow; a runtime without a stdin pipe silently losing the prompt; a possible unhandled rejection in the dialog reply; a call id that fell back to the tool name; a duplicated English plan-review table. The Spec review found the "no code adapted" claim wrong: the plan-review dialog structure and two deny messages follow dsh-oh-my-claude 1.6.2, so a provenance record and a MIT notice were added. Accepted as judgement calls: `--tools default` (kept so `AskUserQuestion` is offered in `-p` runs, as that plugin does; not checked live), the 15 s keep-alive, the "approval prompts disabled" wording, the unsupported-subtype reply, the local service interfaces, shared helpers left unmerged, `runCliAccount` size, and Arabic strings in a host table because host code cannot import the locale files.

## Limits

- No real CLI, sign-in or installed DSH was exercised, so live acceptance (#195) is where these are confirmed: that a real `claude -p` sends `can_use_tool` frames over stdio as the Agent SDK documents, and that DSH's real dialogs return the documented answer shape.
- No `initialize` handshake is sent. dsh-oh-my-claude 1.6.2 uses that request only for subagent progress summaries and next-prompt suggestions, and its own notes say a session runs without it, so it is not a prerequisite for permission requests; this is read from that plugin's behaviour, not from a live run here.
- The question service contract (item and option shape, `custom` and `selected` semantics, `plan-review` needing `detail` and an offered approve label, abort and delegated-caller errors) was read from the published `@deepseek-ai/dsh-user-questions` 0.2.2-rc.1 README and implementation. The installed DSH is 0.2.2-rc.2 and the typings in `node_modules` are 0.2.1-rc.2.
- File delivery is proven only for the text a hand-built message carries; that DSH really produces the handle line is checked in live acceptance (#195).
- The question and plan-review text the CLI supplies is shown as written. Tool results are shown as the CLI returned them and become part of the session text; there is no secret masking, which the ticket does not ask for.
- Existing baseline files touched here (`claude.ts`, the translator) already failed the formatter before this ticket and were not reformatted, to keep the diff to the ticket; new files are formatted.
